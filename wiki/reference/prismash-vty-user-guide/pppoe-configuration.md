# PPPoE configuration

This page is the reference for the `pppoe` block and the `aaa` > `radius` block: the box terminates the subscribers' PPPoE sessions, authenticates each one against your RADIUS, limits the bandwidth of each session and translates their traffic through the CGNAT, as it does with a subscriber behind an `inside` interface. It says what each statement does, what the box refuses and how to read the sessions. To bring the box up as a BNG for the first time, in order, see [Bring PPPoE subscribers online, step by step](/s/wiki-en/doc/bring-pppoe-subscribers-online-step-by-step-c0J39qphvJ).

```
prisma> configure
prisma# [edit] aaa
prisma# [edit aaa] radius
prisma# [edit aaa / radius] server 192.0.2.10 secret <secret> priority 1
prisma# [edit aaa / radius] server 192.0.2.11 secret <secret> priority 2
prisma# [edit aaa / radius] exit
prisma# [edit aaa] exit
prisma# [edit] pppoe
prisma# [edit pppoe] interface enp2s0
prisma# [edit pppoe] gateway 100.64.0.1
prisma# [edit pppoe] address-pool 100.64.0.10-100.64.3.250
prisma# [edit pppoe] dns 8.8.8.8
prisma# [edit pppoe] exit
prisma# [edit] commit
```

The `commit` generates the PPPoE control plane configuration from the candidate and puts it live. Like everything else, the change goes into `rollback`, `commit confirmed` and the audit trail. The files the control plane reads are generated by the box and rewritten at each commit; they are not edited by hand.


:::warning
Every change in the `pppoe` block restarts the PPPoE control plane: **all sessions drop** and the CPEs dial again. Forwarding for other subscribers, routing and the VTY are not affected. A change only in `aaa` > `radius` (one more server, another mode, another timeout) **drops no one**: the control plane rereads the RADIUS configuration with the sessions up. The exceptions are the first server (PPPoE goes from local users to RADIUS) and `dynamic-authorization`, which restart it.

:::

## Statements

| Statement | What it does |
|-----------|--------------|
| `interface <name>` | an access interface: the card, or a sub-interface of it with **one** VLAN tag (`vlan <id>` in the sub-interface block). There can be several, all on the same card |
| `gateway <address>` | the box's address in each session (the IPCP local address). Mandatory |
| `address-pool <prefix>` or `<first>-<last>` | addresses for those to whom RADIUS does not send `Framed-IP-Address`. Up to 16 |
| `dns <address>` | a resolver handed to the CPE. Up to 2 |
| `authentication pap chap mschap-v2` | the methods offered; all three if omitted |
| `session-limit <n>` | at most this many sessions; 16,000 if omitted. Each session is an interface in the dataplane, and the statistics segment is sized for this number at boot, from the saved configuration. `commit` refuses more than 100,000 (the measured maximum) and more than the box's RAM lets the segment hold; until the next reboot, the box accepts only what the segment in use holds, and `show pppoe summary` says so |
| `mtu <576-1500>` | PPP MTU and MRU; 1492 if omitted |
| `tcp-mss <536-1460>` | clamps the TCP MSS on each session; on the session's IPv6, 20 bytes lower |
| `rate-limit default <download>/<upload>` | the bandwidth limit of a session for which RADIUS sent none, in kbit/s or with K, M or G (`20M/10M`); without it, that session has no limit |
| `rate-limit download shaper` or `policer` | how the download limit is enforced: by a queue (shaper, the default) or by dropping (policer). See [Queue or drop](#queue-or-drop-shaper-and-policer) |
| `rate-limit upload shaper` or `policer` | the same for the upload; policer if omitted |
| `ac-name <name>` | the concentrator name in the PADO; `prisma-routing` if omitted |
| `local-user <name> password <password>` | a local user, for a lab without RADIUS |
| `ipv6 prefix-pool <prefix>` | turns on IPv6 on the sessions; each session receives a /64 from this prefix as WAN, announced by RA (SLAAC). From /16 to /64. Up to 16 |
| `ipv6 delegated-pool <prefix> length <n>` | a `/n` prefix from this one for each session, delegated by DHCPv6 (prefix delegation) to the customer's LAN. Up to 16 |
| `ipv6 dns <address>` | an IPv6 resolver handed to the CPE, in the RA and in DHCPv6. Up to 2 |
| `ipv6 enable` | turns on IPv6 without a pool: the prefixes come only from RADIUS |

`no <statement>` undoes each one; `no pppoe`, at the top of configuration mode, removes the whole block and turns off the PPPoE control plane at `commit`.

RADIUS is no longer inside `pppoe`: it is in `aaa` > `radius`, below. Typing `radius ...` inside `pppoe` is refused with the new location. A box that came from 0.154.0 with `radius server ...` in the `pppoe` block needs nothing: when loading the saved configuration, each of those lines becomes its equivalent in `aaa` > `radius`, with the same secret, in the same order (the first server gets `priority 1`), and the box warns line by line and rewrites the file.

## RADIUS: `aaa` > `radius`

| Statement | What it does |
|-----------|--------------|
| `server <address> secret <secret> [auth-port <n>] [acct-port <n>] [role auth\|acct\|both] [priority <1-255>]` | a server. Ports 1812 and 1813 if omitted. `role auth` only authenticates, `role acct` only receives accounting, `both` (the default) both. `priority`: the lowest is tried first; without it, the server goes after the last one. Up to 8 |
| `mode failover` or `mode round-robin` | how the servers are used; `failover` if omitted |
| `timeout <1-60>` | seconds a request waits for an answer; 3 if omitted |
| `retries <0-10>` | resends to the same server before moving to the next; 1 if omitted |
| `dead-time <1-3600>` | seconds a server that did not answer stays out; 30 if omitted |
| `nas-identifier <name>` | the NAS-Identifier sent; `prisma-routing` if omitted |
| `interim-interval <seconds>` | interim accounting updates: 0 (none) or 60 to 86400; 300 if omitted |
| `dynamic-authorization listen <address> [port <n>]` | where the box receives Disconnect and CoA (RFC 5176); port 3799 if omitted |
| `dynamic-authorization client <address> secret <secret>` | a server that can send Disconnect and CoA, with its secret. Up to 16 |
| `rate-profile <name> down <rate> up <rate>` | the rates that a `Cisco-AVPair` `sub-qos-policy` with that name means (below). Up to 64 |

`**failover**`: every request goes to the server with the lowest `priority`. If it does not answer within `timeout` seconds, `retries` times, the request goes to the next one, and the one that did not answer stays out for `dead-time` seconds: the next subscriber already goes straight to the next one. With the defaults, a dead server costs **one** subscriber 6 seconds and the others none. Once the `dead-time` passes, it becomes the first again. Two servers with the same `priority` share the load between them.

`**round-robin**`: each request goes to the next active server, in rotation. Accounting-Starts also rotate; the Interims and the Stop of a session always go to the server that received its Start.

Accounting follows the same choice, among the servers that receive accounting; the Interims and the Stop of a session go to the server that received its Start, as long as it answers. With no accounting server (all `role auth`), accounting is off, and `show pppoe summary` says so.

A session is never dropped because accounting went unanswered.

```
prisma# [edit aaa / radius] server 192.0.2.10 secret <secret> priority 1
prisma# [edit aaa / radius] server 192.0.2.11 secret <secret> priority 2
prisma# [edit aaa / radius] server 192.0.2.20 secret <secret> role acct priority 3
prisma# [edit aaa / radius] dynamic-authorization listen 10.0.0.1
prisma# [edit aaa / radius] dynamic-authorization client 192.0.2.10 secret <secret>
```

## Per-subscriber bandwidth limit

Each session's limit comes from RADIUS, in the Access-Accept, in two of Prisma's own attributes (vendor 67033, the product's IANA number):

| Attribute | Number | Type | What it is |
|-----------|--------|------|------------|
| `Prisma-Rate-Limit-Down` | 1      | integer | download (from the box to the subscriber), in kbit/s |
| `Prisma-Rate-Limit-Up` | 2      | integer | upload (from the subscriber to the box), in kbit/s |

0, or the attribute absent, is no limit in that direction. `20000` is 20 Mbit/s. The maximum is 10 Gbit/s.

`Cisco-AVPair` is also read, when the packet carries no Prisma attribute (if it carries both, Prisma's wins):

| `Cisco-AVPair` | What it limits |
|--------------|----------------|
| `lcp:interface-config=rate-limit output <bps> <burst> <burst-max> conform-action transmit exceed-action drop` | the download, in bits per second |
| `lcp:interface-config=rate-limit input <bps> ...` (the same format) | the upload: `input` is what the box receives from the subscriber |
| `lcp:interface-config#1=...` | the same, in numbered form |
| `ip:sub-qos-policy-out=<name>` or `subscriber:sub-qos-policy-out=<name>` | the download of the `rate-profile` with that name |
| `ip:sub-qos-policy-in=<name>` or `subscriber:sub-qos-policy-in=<name>` | the upload of the `rate-profile` with that name |

A policy carries only a name; the rate it means is configured on the box, in `aaa` > `radius`:

```
prisma# [edit aaa / radius] rate-profile PLANO_100M down 100M up 50M
```

A rate `Cisco-AVPair` outside these formats (a `rate-limit` with `access-group`, without the actions, a rate with a suffix) makes **none** of the packet's Cisco rates apply, and the box logs the reason: half a plan is not a plan. A name without a `rate-profile` leaves that direction unlimited, also logged. `Mikrotik-Rate-Limit` is not read.

The dictionary to install on your RADIUS server comes from the box itself:

```
prisma> show aaa radius dictionary
```

On FreeRADIUS, save what this command prints as `/usr/share/freeradius/dictionary.prisma` and add `$INCLUDE /usr/share/freeradius/dictionary.prisma` to the file `/etc/freeradius/3.0/dictionary`. On IXC or another system, register vendor 67033 and the two attributes in the table.

The upload is enforced by a policer in the dataplane, on the session's own interface: what exceeds the limit is dropped. The download, by default, by a queue (the next section); with `rate-limit download policer`, also by a policer. The accepted burst (the policer bucket) is half a second of the rate, never less than 15,000 bytes, whether the rate comes from the Prisma attributes or from `Cisco-AVPair`: the `Cisco-AVPair` burst numbers are checked and not used. Half a second is what lets **one** TCP connection, such as a speed test's, reach the plan: with a tenth of a second (0.155.1) it reached half (25 Mbit/s on a 50 plan), even though UDP passed exactly. Up to 0.155.0 the bucket was eight times larger, and a short test measured 7% to 90% above the plan. A session without a RADIUS limit gets the `rate-limit default` of the `pppoe` block, if any.

### Queue or drop: shaper and policer

By default, each session's **download** goes through a queue of its own in the dataplane (the shaper): what arrives above the plan waits in the queue and leaves at the plan's pace, instead of being dropped. The queue holds up to 100 ms of the plan (25,000 bytes on a 2 Mbit/s plan, 250,000 on a 20 Mbit/s one). So that a TCP download does not keep it full, the box drops a packet now and then while the wait exceeds 15 ms (CoDel). The **upload** stays on a policer: what exceeds the plan is dropped.

Measured on a 20 Mbit/s plan, the shaper against the policer:

|     | shaper | policer |
|-----|--------|---------|
| one TCP connection | 19\.3 Mbit/s, 17 retransmissions | 19\.7 Mbit/s, 823 retransmissions |
| ping during that connection | 25 ms  | 12 ms   |
| four connections sharing the plan | evenly (Jain 0.994) | unevenly (Jain 0.832) |
| UDP at 40 Mbit/s | the plan gets through, 19.6 | the plan gets through, 20.3 |
| ping during that UDP | up to 104 ms: the queue full | 12 ms   |

The shaper measures the plan in IP bytes, without the PPPoE and Ethernet headers, so a TCP speed test reads a little below 20 (the maximum is 19.47). A subscriber sending UDP above the plan non-stop waits, in their own traffic, up to the size of the queue; the other subscribers' traffic is not affected.

To go back to the policer on the download:

```
prisma# [edit pppoe] rate-limit download policer
```

`no rate-limit download` goes back to the default. The switch, in either direction, restarts the PPPoE control plane: all sessions drop and dial again, already with the new choice. `show pppoe summary` says what enforces each direction.

An NMS follows the queues over SNMP, in `prBngShaper`: what enforces each direction, the queues now and the packets that passed, waited and were dropped, summed over the whole box (see [Monitoring and SNMP](/s/wiki-en/doc/monitoring-and-snmp-GxrrkTSEJT)).

When upgrading a box that already has PPPoE, the control plane's files are rewritten at the next load of the configuration. At that moment the sessions dial again, once, and the download moves to the shaper.

## IPv6

Without any `ipv6` statement, the session stays IPv4 only, as before: a CPE that asks for IPv6 is refused. With them, each session negotiates IPv6CP and receives two prefixes:

* **the WAN one**, a /64, announced by Router Advertisement: the CPE builds its own address in it (SLAAC). It comes from RADIUS's `Framed-IPv6-Prefix` when it sends one, and from `ipv6 prefix-pool` when it does not;
* **the delegated one**, for the customer's LAN, handed out by DHCPv6 when the CPE asks (prefix delegation). It comes from RADIUS's `Delegated-IPv6-Prefix` when it sends one, and from `ipv6 delegated-pool` when it does not.

```
prisma# [edit pppoe] ipv6 prefix-pool 2001:db8:100::/40
prisma# [edit pppoe] ipv6 delegated-pool 2001:db8:200::/36 length 56
prisma# [edit pppoe] ipv6 dns 2001:4860:4860::8888
```

The box is `fe80::1` on every session; it is the CPE's default router. Both prefixes are routed in the dataplane to the session: the subscriber's IPv6 traffic is routed, not translated by the CGNAT. The session's bandwidth limit applies to IPv6 too, in the same bucket as IPv4: a 20 Mbit/s plan is 20 Mbit/s adding both.

RADIUS receives in accounting the `Framed-IPv6-Prefix` and the `Framed-Interface-Id` already in the Accounting-Start, and the `Delegated-IPv6-Prefix` in an interim update sent at the moment the prefix is delegated.

## Disconnect and CoA

With `dynamic-authorization`, your RADIUS (or IXC) can, without the subscriber dialing again:

* **drop a session** with a Disconnect-Request, identifying it by `User-Name` or by `Acct-Session-Id`. The box answers Disconnect-ACK, the session drops and the Stop goes out with `Acct-Terminate-Cause = Admin-Reset`;
* **change the bandwidth limit** with a CoA-Request with `Prisma-Rate-Limit-Down` and/or `-Up`, or with a rate `Cisco-AVPair`: it takes effect immediately, on the live session. An absent direction stays as it was; 0 removes the limit in that direction;
* **give the session a deadline** with `Session-Timeout` in a CoA-Request: it drops when it expires.

A CoA-Request with an attribute the box does not apply (a `Mikrotik-Rate-Limit`, a `Filter-Id`), a rate above 10 Gbit/s, a malformed rate `Cisco-AVPair` or a `sub-qos-policy` without `rate-profile` is refused in full with CoA-NAK, and nothing changes. A request from an address that is not a `client`, or with the wrong secret, gets no answer at all.

Each session's address comes from RADIUS (`Framed-IP-Address`) when it sends one, and from `address-pool` when it does not. For the CGNAT to translate the sessions, the addresses they receive must be in a pool's `prefix-inside`, like those of any subscriber.

## What commit refuses

| Situation | Why |
|-----------|-----|
| no `interface`, no `gateway` | the control plane would have nowhere to answer and no address to use |
| no server in `aaa` > `radius` and no `local-user` | no one to authenticate |
| no `address-pool` and no RADIUS | no one to hand out addresses |
| `ipv6` without `ipv6 prefix-pool` and without RADIUS | no session would have a WAN prefix, and without it the CPE does not ask for the delegated one |
| two IPv6 pools that overlap | the same prefix would go to two subscribers |
| servers in `aaa` > `radius`, none that authenticates (all `role acct`) | no one to authenticate |
| `dynamic-authorization listen` without `client`, or `client` without `listen` | no one could sign a request, or there would be nowhere to receive it |
| access interfaces on two cards | the dataplane PPPoE answers from a single MAC |
| a sub-interface with two tags (QinQ) | the dataplane PPPoE reads a single tag |
| a sub-interface without `vlan <id>` in its block | there would be no tag to answer on |
| two access interfaces with the same VLAN | both would be the same port |
| an interface the dataplane does not have | nothing to answer on it |
| a secret with a space, comma, quotes or `#` (refused as soon as it is typed) | it would break the generated configuration |

## The RADIUS secrets

The secret of each server and each `client` is kept in the saved configuration, so that a `rollback` can restore it, and **never appears on a screen**: `show running-config`, `show configuration` and `show configuration compare` show `<set, not shown>`. In a `compare`, changing the secret appears as one removed line and one added line, neither with the value. A `local-user` password is treated the same way.

## Sessions

| Command | What it shows or does |
|---------|-----------------------|
| `show pppoe sessions` | one line per session: the id, the user, the address, the limit (download/upload, `-` with no limit) and how long it has been up; a session still authenticating says `start` in place of the time. A session with IPv6 has below it an `ipv6` line with the WAN prefix and a `delegated` line with the delegated prefix |
| `show pppoe session <id>` | an entire session: the IPv6 prefixes, the CPE's MAC, the traffic and the limit. For each direction limited by a policer, how many packets it let through and how many it dropped. For each direction with a shaper, what is in the queue now, how many packets passed straight through and how many waited, how long they waited (average and maximum) and what was dropped: queue full, CoDel, or the box's buffers |
| `show pppoe summary` | whether the PPPoE control plane is running, how many sessions are active, starting and ending, each RADIUS server (with `failed` if the control plane marked it as down) and the configuration summary |
| `clear pppoe session <id>` | ends a session; the id is the one in the first column of `show pppoe sessions`, the same `Acct-Session-Id` RADIUS received |
| `clear pppoe session user <name>` | ends a user's sessions |
| `clear pppoe session address <A.B.C.D>` | ends the session that has that inside address, found in `show pppoe sessions` |
| `clear pppoe session all` | ends all              |

An ended session sends PADT to the CPE and Accounting-Stop to RADIUS; the CPE dials again. The interfaces the dataplane creates for the sessions never go into the configuration: they are subscribers dialing, not something someone configured.

All of this is also in the management API (gRPC), with typed fields: the sessions, a session with its policers, the summary with the history and refusal counters, the history and chain verification, and `clear` by id, user, address or all. The `pppoe` and `aaa` blocks are read and written as fields by `GetConfig` and `SetConfig`; secrets never come back on a read.

## Who had the address: the session history

With PPPoE, the subscriber's inside address is handed out at dial time, first come first served. The CGNAT record (the block log, or the formula) says which **inside address** was behind a public IP and a port; to know **which subscriber** had that address at that instant, the box keeps its own session history. It is written by the control plane at the start and end of each session, whether or not any RADIUS server answers, in `/var/log/prisma-routing/pppoe-sessions.log`, next to the configuration trail: it only grows, each line goes to disk before the session proceeds, and each one carries a hash chained to the previous one. On a session with IPv6, the start line carries the WAN prefix, and the delegated prefix goes on its own line at the moment it is delegated, repeated at the end of the session.

| Command | What it shows |
|---------|---------------|
| `show pppoe history address <A.B.C.D> at <time>` | the session that had that inside address at that instant: the user, from when to when, the session id, the MAC and the access interface |
| `show pppoe history address <IPv6 address> at <time>` | the session whose WAN prefix contains that address, or whose delegated prefix contained it at that instant: the delegated one counts from the time it was delegated, not from the start of the session |
| `show pppoe history user <name>` | a user's sessions |
| `show pppoe history session <id>` | one session, by its id |
| `show pppoe history since <time>` | the sessions that were up from that time onward |
| `show pppoe history last <n>` | only the last `n` sessions; also after a filter (`user`, `address`, `since`) |
| `show pppoe history verify` | checks the hash chain and gives the first line that does not match |
| `show cgnat translation <public> <port> at <time>` | on a deterministic pool, both steps at once: the inside address by the formula and the session that had it at that instant |

The time is the one from `show log`: an ISO time with `Z` (the block log's, copied as is), without a time zone (the box's), or `30m`, `2d` back. The times the history shows are always UTC, like those of the block log.

```
prisma> show pppoe history address 100.64.0.11 at 2026-10-13T02:51:00Z
maria.souza held 100.64.0.11
  from 2026-10-13T02:49:02.789Z  to still held
  session 7f3a0c1e00000005  mac 02:aa:00:00:00:05  on enp2s0.100
```

On a **dynamic** pool, the block belongs to whoever has it now: `show cgnat translation` answers only for now and refuses `at`. For a past instant, the `BLOCK-ALLOC` line of the block log whose range contains the port gives the inside address and the time, and `show pppoe history address <address> at <time>` gives the subscriber.

`show pppoe summary` has the `session trail` line: how many lines were written and, in capitals, how many could **not** be (volume full, for example) - each one is a session the box cannot answer for.


:::warning
A chain that checks out proves the file was not edited, not that it is the same file. That is why the box sends the head of the chain off the box: every hour while the history grows, when the event watcher starts, and the last line of each month when the file is rotated, it records a `trail` event with the `seq` and the `sha256` — and the event log goes to the syslog collectors configured in `system` > `logging` and to the API's `WatchEvents`. To check, compare the `head seq` and the `sha256` from `show pppoe history verify` with the last `trail` event the collector received (`show log kind trail` shows the box's own copy). Without a syslog collector configured, that copy does not leave the box. The box never deletes the history: once a month the file becomes `pppoe-sessions.log.<YYYY-MM>`, and the months beyond the retention period can be archived or removed by you.

:::

## Where the box accepts PPPoE

**Only on the access interfaces.** A PADI, or any PPPoE frame, that arrives on an interface that is not in the `pppoe` block — the uplink, a CGNAT `inside` port — is dropped in the dataplane and counted; no one answers. Before this, a CPE on the wrong side of the box received PADO and could open a session.

**A MAC belongs to the port where its session is.** If the same MAC appears on two access interfaces (a cloned CPE, or two OLTs with the same address), the box **keeps the session that already exists** and refuses, counting them, the discovery and control from that MAC coming from the other port while the session is alive. As soon as the subscriber disconnects there (their PADT), or 60 s after the session's last sign of life (the same time the control plane would take to declare it dead), the other port can dial. Without this, both sessions existed together and each control frame went to the port that had spoken last: one subscriber received the control of the other's session.

```
prisma> show pppoe summary
```

What was refused is in the dataplane's `show bpa pppoe-access`, in two lines — `discovery` and `session` — with how many frames passed, how many arrived on an interface that is not an access one (`not-access`) and how many carried a MAC that belongs to another port (`held`).


:::info
Two **different** subscribers with the same MAC on two ports are not served at the same time: the dataplane identifies the session by the MAC and the session number, without the port. The first one stays; the second waits.

:::

## The log: `show log`

Each start and each stop of the PPPoE control plane goes into the box's log with the reason, as does each RADIUS server the control plane marks as down, and back up:

```
prisma> show log kind start
prisma> show log kind exit
prisma> show log kind radius
```

| Event | Example |
|-------|---------|
| start requested by a commit | `the PPPoE control plane (prisma-bng) started again: PPPoE's configuration committed by ana` |
| exit due to failure, with the code or signal | `the PPPoE control plane (prisma-bng) exited with code 1: accel-pppd was killed by signal 9 (KILL)` |
| the start that came after it, with no one asking | `the PPPoE control plane (prisma-bng) started again, by its restart policy, after it exited: ...` |
| requested stop (commit, upgrade, `no pppoe`) | `the PPPoE control plane (prisma-bng) stopped: stopped (SIGTERM): ...` |
| restart in an upgrade that rewrites the files | `... started again: PPPoE's files from an older release (format 6) written again in format 7` |
| RADIUS server down, and back | `RADIUS server 192.0.2.10 failed: it did not answer, ...` / `RADIUS server 192.0.2.10 is active again: ...` |

A start at `warning` level is one nobody asked for: that is the one worth investigating.

## How to verify

```
prisma> show pppoe summary
prisma> show pppoe sessions
```

The summary should say `running` and count the active sessions; each subscriber who dialed appears in `show pppoe sessions` with the address they received. On your RADIUS, each session leaves an Accounting-Start, the interim updates with the session bytes and, when it drops, an Accounting-Stop.


:::info
QinQ and high availability of sessions do not exist yet. A session is always IPv4 with optional IPv6: IPv6-only does not exist. The shaper has one queue per session, not one per connection: UDP above the plan makes the rest of the subscriber's own traffic wait.

:::
